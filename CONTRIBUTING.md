# Contributing to Moderne Docs

We encourage you to contribute to our docs! Please feel free to create an issue or open a PR if you find any issues.

We use [Docusaurus](https://docusaurus.io/) to manage our documentation. When any changes are merged into this repository, a build is kicked off to update the docs. See the [README](./README.md#getting-started) for how to install dependencies and preview the site locally.

## Writing standards

Follow the [style guide](./STYLE_GUIDE.md). It covers markdown formatting, file naming, link paths, and tone. The `yarn lint:markdown` command checks the mechanical rules, and CI runs it on every PR.

New pages must be added to `sidebars.ts` or they will not appear in the navigation.

## Auto-generated content

Some files are regenerated by scheduled workflows, and any manual edits to them will be overwritten. Fix the upstream source instead:

* `docs/user-documentation/recipes/recipe-catalog/`, `docs/user-documentation/recipes/lists/`, and `src/plugins/latest-versions.js` are produced by the [rewrite-recipe-markdown-generator](https://github.com/openrewrite/rewrite-recipe-markdown-generator) from the recipe modules themselves. To change a recipe page, fix the recipe's name, description, or options in its source repository.
* `static/marketplace/recipes-v5-*.csv` is built by installing those same recipe modules with the Moderne CLI.
* `docs/user-documentation/moderne-platform/references/graphql-api-reference.md` and `static/graphql/schema.graphql` come from the live GraphQL schema.
* `docs/releases/proprietary-recipe-changelog.md` is assembled from the GitHub releases of the repositories listed in `.github/data/proprietary-repos.txt`.

## Before opening a pull request

Run `yarn build` and fix any warnings or broken links it reports. CI runs the same build, plus `yarn lint:markdown`, `yarn validate:css`, and `yarn typecheck`.

## Pull request descriptions

Write for a reviewer who will read the diff. Tell them why the change exists and anything they can't see from the diff, then stop.

* Lead with the problem, then what the change does, in a few sentences of plain prose.
* Stay under 150 words unless the change genuinely needs more. Most docs PRs need one or two paragraphs.
* No headers or sections for a PR that touches a handful of pages.
* Don't list the files you changed. The diff shows that.
* Don't describe what the PR does not change, what you assumed, or how you verified it, unless a reviewer would otherwise have to ask.
* Don't argue for the approach against alternatives you didn't take unless the reason is non-obvious.
* Link related issues or PRs.

If an AI tool drafts your description, give it these rules. Left alone it will produce a sectioned report several times longer than the change deserves.

A good description for a change that redraws a diagram and touches four files:

> The v2 architecture diagram showed a partial view of the platform, with generic "Moderne Worker" and "Recipe Execution" boxes and no indication that several services are only deployed when a tenant opts into a capability.
>
> Redrew it from the per-service deploy files so each microservice appears by name, split into core services and optional ones gated behind a capability flag. Also published the diagram source as an editable .excalidraw file, matching what the v1 page already does.

## Commit messages

The same rules apply to commit messages. A subject line under 72 characters that says what the change does is usually enough. If the change needs explaining, add one short paragraph on why, not a list of what the diff already shows.

Don't add `Co-Authored-By` or similar trailers for AI tools.
